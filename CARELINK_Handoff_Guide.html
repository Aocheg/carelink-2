CARELINK — Implementation Summary & Handoff Guide

Version: 0.1.0   Date: 19 September 2026

CARELINK is an independently built FastAPI application for clinical care coordination. It provides a database-backed REST API for the eight requested clinical workflow areas and a lightweight browser landing page.

What has been implemented

AreaImplemented capability
FoundationFastAPI, SQLAlchemy 2.x, SQLite configuration, safe explicit database initialization, OpenAPI documentation and UTC-aware input validation.
Patients & admissionPatients with CARELINK numbers, possible-duplicate flag, next of kin, facilities, wards, beds, users, and transactional admission/bed occupancy.
VitalsComplete, partial and not-measured states; paired blood pressure; range validation; admission history; documented abnormal-vital alert generation.
MedicationActive medication orders and administrations, including refusal/held/not-administered reason rules.
InvestigationsMulti-test requests with controlled REQUESTED → PROCESSING → AVAILABLE lifecycle and critical-result alerts.
Clinical workflowsDoctor reviews, clinical orders, structured nursing handover, alerts with acknowledge/resolve lifecycle, and transactional discharge.
AuditabilityAudit records for important creates, transitions, alert actions, and discharge; the calling service owns the transaction.

Run the application

  1. Create and activate a Python 3.12+ virtual environment.
  2. Install: pip install -e '.[dev]'.
  3. Copy .env.example to .env if needed.
  4. Create tables: python -m app.database.init_db.
  5. Start: uvicorn app.main:app --reload.

Use /docs for interactive API documentation, /app for the browser workspace and /health for service status.

Recommended API workflow

  1. Create a user; use role DOCTOR for prescribing, reviews and discharge.
  2. Create a facility, ward and bed.
  3. Create a patient and optionally add next of kin.
  4. Create an admission. This occupies the selected available bed.
  5. Record vitals, medications, investigations, reviews, handovers and alerts against the admission.
  6. Move each investigation item to processing before entering its result.
  7. Acknowledge or resolve relevant alerts.
  8. Discharge using a doctor user. This returns the bed to AVAILABLE atomically.

Important business rules

  • The bed must belong to the selected ward and be AVAILABLE before admission.
  • Vital and medication-administration timestamps require a timezone and are normalized to UTC.
  • COMPLETE vitals require all values; PARTIAL requires some values plus a reason; NOT_MEASURED requires no values and a reason.
  • Administration is permitted only for ACTIVE medication orders. Reasons are required for NOT_ADMINISTERED, REFUSED and HELD.
  • Results cannot become available before an investigation item is processing.
  • SpO₂ below 90% or systolic BP at least 180 creates a HIGH abnormal-vital alert.
  • Only an ACTIVE admission may be discharged; discharge requires an active DOCTOR user.

Production follow-up

Important: Passwords use a one-way scrypt hash, but the current build does not yet implement login/JWT authentication or request-bound role authorization. Add these, migrations, a richer frontend, access controls, logging/monitoring, encryption/key management, backups and formal clinical governance review before production use.
